# Ubuntu / open-weight モデルによるサイト改善計画

作成日: 2026-10-06。実装前の提案。実装方針とマージは人間が判断する。

進捗: #79の再起動でGPU不整合を解消し、VRAM 8192MiBと既存サービス復帰・GPU推論を確認済み。
#78の初期実装・試行手順は[Ubuntuレビュー運用手順](ubuntu-review-runbook.md)を参照。
以下の環境表は復旧前の調査記録として残す。

## 目的と優先順位

1. 今後3か月の公演の取りこぼし・更新漏れを減らす。
2. Search Console / GA4の実測から検索流入とチケット送客を改善する。
3. 小さなUI改善と保守を、根拠・差分・検証結果付きで人間へ渡す。

ニュース記事の量産、無承認の公開、モデルによる自己承認は行わない。
サイトはVercelの現行構成を維持し、Ubuntuは裏側の調査・開発作業に使う。

## モデルと役割

8GB級GPUを前提に、最初は同時推論数1、コンテキスト4K、必要時のみ8Kで評価する。
役割ごとにプロンプト・入力・出力を分離し、同じモデルも別セッションで使う。
モデル名・量子化・digest・プロンプト版を実行記録に残す。以下は採用候補であり速度保証ではない。

| 役割 | 初期モデル候補 | 入力 → 成果物 |
| --- | --- | --- |
| 公演調査・抽出 | 既存qwen3-vl:4bを評価。精度不足ならQwen3-8Bの4bitと比較 | 公式ページの抜粋 → 根拠URL付き候補JSON・ツアー全日程の確認結果 |
| フライヤー補助 | 既存qwen3-vl:4b / 8bを必要時だけ使用 | 公式画像 → 日時・会場の読み取り案。画像由来と不確実箇所を明記 |
| 成長分析・提案 | Qwen3-8Bの4bitを評価 | 月次GSC / GA4集計・サイト構成 → 優先度付き改善Issue |
| 実装 | Qwen2.5-Coder-7B-Instructの4bitを評価 | 人間が承認したIssue・関連ファイル → 小さなブランチ差分・Draft PR |
| 独立レビュー | Qwen3-8B、必要ならCoderも別セッション | Issueの受入条件・差分・検証ログ → 指摘・残る不確実性 |
| 進行管理 | LLMではなくNodeスクリプト | 承認状態・実行記録 → 次ジョブ・Issue通知 |

モデル間の一致を正しさの証明にしない。公式根拠、決定的な検証、人間の確認を優先する。
30B級を初期の常用モデルにはしない。RAMオフロード可能性より、待ち時間と運用の単純さを優先する。

## 既存実装を使う構成

`systemd timer → Nodeジョブ管理 → ローカルOllama → 検証 → GitHub Issue / Draft PR`

- `scripts/site-review-agent.mjs` は既にローカル互換APIに対応。Ubuntu移行の最初の対象。
- `scripts/research-candidates.mjs` は外部APIのURLが固定。ローカルAPIのbase URL・model・任意認証・タイムアウトを設定可能にする小変更を別Issueで承認する。
- `research:links`、compact prompt、`watchTargets.ts`、既存の分析レポートを再利用する。
- 最初のジョブは分析・通知だけ。実装ジョブは承認の読み取りが検証できてから追加する。
- キューはローカルJSONとファイルロックで開始。run ID、Issue ID、base SHA、状態、モデル、開始終了、結果を記録。再実行は同じキーで重複通知を避ける。
- GPUジョブを直列化し、既存draw2cad作業との利用時間を調整する。失敗時は最大1回再試行し、以後は停止してIssueで通知する。
- 最初は1ジョブ20分、1日合計60分を上限案とし、実測して人間が調整する。
- 既存Actionsは試行中維持。移行確認後に同じ仕事の定期実行を停止し、二重収集・二重Issueを防ぐ。検証CIは維持する。

## 人間の判断をIssueへ集約する

状態: `提案 → 方針承認待ち → 実装中 → 人間レビュー待ち → 完了`。
保留・失敗・方針変更は同じIssueに追記する。

1. AIが課題・根拠・実装案・変更範囲・検証方法をIssueに書く。
2. 人間が対象案の版を指定して承認コメントを残す。無応答・AIコメント・ラベルだけでは承認扱いにしない。
3. ジョブ管理が許可された人間のGitHubユーザーIDと対象版を検証する。承認がない実装ジョブは開始しない。
4. Issue単位の隔離worktreeで実装し、検証後にDraft PRを作る。承認範囲が変わればIssueに改訂案を書き、再承認を待つ。
5. 同じIssueへPR、変更要約、検証結果、レビュー指摘、残るリスクを通知する。
6. 人間がPRを確認してマージする。botにmainへの直接push・自動マージ・承認操作を許さない。
7. マージ後の結果と、必要なら28日後の効果測定を元Issueに追記する。

Issue本文の共通項目:

```text
課題 / 利用者への影響:
根拠URL・集計期間・観測値:
提案v1 / 代案 / 推奨理由:
変更するファイル・対象外:
受入条件 / 検証コマンド / 戻し方:
人間に判断してほしい点:
承認記録（人間・案の版・コメントURL）:
実装結果 / PR / 検証ログ / 未解決事項:
```

同じ課題は既存Issueに追記し、新規提案は原則週3件まで。失敗・承認待ち・PR準備完了はその都度通知する。
既存 #24 / #27 / #33 / #34 / #35 / #37 / #39 とロードマップの完了状況に差があるため、最初に実装状況を照合する。勝手にcloseしない。

## 候補収集と公開の区別

- 新規は`src/data/candidate_events.ts`、公開済み更新は`src/data/event_update_candidates.ts`へ分ける。
- 収集範囲・頻度の承認後は、その範囲の収集を継続。候補PRのマージは人間が行う。
- PRブランチの候補は、そのブランチを起動したローカル環境で確認するか、人間のマージ後に管理画面で確認する。本番管理画面に未マージ候補が見えるとは扱わない。
- 候補Issueは通知のみ。内容の公開・無視は`/admin/candidates`で人間が決める。
- robots.txt、取得間隔、raw HTML保存、source-specific収集を維持。SNSが取得できなければ手動X確認リストを毎回残す。
- 日付・会場・出演者の根拠を残し、ツアーは他の日本公演も確認。失敗・取得不可を「公演なし」に変換しない。

## 実行権限と停止条件

分析用の読み取り環境と、実装用の隔離環境を分ける。実装環境には本番・SSH・分析APIの秘密情報やDockerソケットを渡さない。
GitHub書き込みはジョブ管理側に限定し、必要最小限の権限とmain保護ルールを確認する。
取得HTMLやIssue本文は資料として扱い、そこに書かれた命令を実行権限に変換しない。
モデルAPIはlocalhostのまま使う。シェルコマンドは承認済み作業と許可した検証に限定する。
GPU障害、承認判定エラー、公開データへの意図しない変更、連続失敗は該当ジョブを止めて通知する。

## 段階導入と受入条件

| 段階 | 作業 | 次へ進む条件 |
| --- | --- | --- |
| 0: 基盤 | GPU不整合の復旧、分離Node 24、既存Ollama共有方針、モデル評価 | nvidia-smi成功、GPU使用を確認、既存サービス正常、20件の保存ページで抽出比較 |
| 1: 提案だけ | site-reviewを手動実行→定期化、Issue重複防止 | 1週間、無承認変更ゼロ、同一課題の重複Issueゼロ、役立つ提案を人間が確認 |
| 2: 候補収集 | ローカルAPI対応、既存収集との比較 | 評価20件で日付・会場の根拠一致19件以上、捏造ゼロ、ツアー漏れ明記、不明を棄却できる |
| 3: 小変更の実装 | 承認確認、worktree、Draft PR、別セッションレビュー | 未承認・改訂後未承認の起動拒否を確認。小変更3件で全必須チェック成功、人間がマージ可否を判断 |
| 4: 成長の反復 | 月次分析→最大3提案→承認→改善→翌月比較 | チケット送客・検索クリック・人間の確認時間を継続記録できる |

実装・データ変更の必須チェック:

```bash
npm run data:validate
npm run copy:check
npm run lint
npm run build
```

UI変更はモバイル表示と主要操作も確認。検証失敗のPRはマージ待ち扱いにしない。
ドキュメントだけの場合は`git diff --check`を基本とする。

最初の評価はモデルごとにJSON成功率、日付/会場の一致、捏造・重複・ツアー漏れ、処理時間、GPU/RAM最大使用量を記録する。
数値は初期の受入目安で、実績ではない。サンプル外の網羅性も保証しない。

## 成長を測る

- 最優先: Monthly Ticket Outbound、検索クリック、イベント詳細からのチケットCTR。
- 運用: 公式発表から候補化までの時間、採用率、更新漏れ、週の人間レビュー時間。
- 網羅性: 全公演数は不明なので、承認済み監視ソースの確認率と定点サンプルの掲載率を代理指標にする。
- 月次で前28日と比較し、公演数・季節性・検索順位の変化も記録。AI改善の因果効果と断定しない。
- 候補レビューの滞留が増えたら、モデル数や収集量を増やす前に頻度・提案数を減らす。
